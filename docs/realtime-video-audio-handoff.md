# Creekstone 实时音频驱动视频：对接能力说明

日期：2026-09-21。面向实时视频服务开发方。

本文用于双方制定接口，不是已经开放的第三方 API。音频生成与网站实时播放已实现；服务端到视频服务的适配器、外部鉴权和音视频播放集成尚未实现。

## 1. 我们已具备的能力

Creekstone 的 Agent 正文增量进入服务端 Gateway，经过基础朗读文本清理，再增量发送给 BytePlus / Doubao 双向流式 TTS。TTS 尚未收到全部文字时，即可返回音频分片；无需等待完整回复或完整音频文件。

当前使用既有的克隆音色。只朗读回复正文，不将 reasoning、工具事件直接输入 TTS。代码、链接、附件标记等会经过基础过滤；本流程不是内容安全过滤器。

| 属性 | 当前输出 |
| --- | --- |
| 音频编码 | 原始 PCM，signed 16-bit little-endian（`pcm_s16le`） |
| 采样率 | 24,000 Hz |
| 声道 | 单声道 |
| 每个采样帧 | 2 字节 |
| 原始码率 | 48,000 字节/秒，即 384 kbit/s |
| 文件头 | 无 WAV / MP3 文件头 |
| 分片 | 连续音频字节，分片长度与到达间隔不固定，不保证对应一句话 |
| 数据到达速度 | 可能快于或慢于实际播放速度，不按实时音频时钟匀速发送 |
| 内容结束 | TTS 完成后有独立结束事件，不以某个分片的大小判断结束 |
| 停止 | 可以独立取消语音，不必取消 LLM 文字输出 |
| 字幕 / 音素时间戳 | 当前网站没有启用或转发，不属于现成输出能力 |

当前浏览器传输将 PCM 分片编码为 Base64 并放入 SSE 事件；这只是网站内部传输方式，不是要求视频服务也采用 SSE。Base64 比原始音频约增加三分之一字节数，另有事件封装开销。

PCM 音频可直接作为接受该格式的视频生成系统的输入。若对方要求 16 kHz、48 kHz、Float32、Opus 或固定帧长，需双方确定转换由谁完成；当前集成固定为 24 kHz，不应自行按其他采样率解释。

## 2. 当前网站内部事件（已实现，仅作能力参考）

以下来自网站的独立语音 SSE 通道：

```text
event: ready
data: {"sampleRate":24000,"format":"pcm_s16le","channels":1}

event: status
data: {"phase":"connecting"}

event: audio
data: {"data":"<Base64 编码的 PCM 字节>"}

event: done
data: {}
```

异常时返回 `error` 事件；取消、网络断开和文本请求失败也会终止相应语音生命周期。当前内部事件没有统一的序号或音频时间戳，且取消与自然结束在部分路径上共享 `done`，不能直接当作第三方完整协议。对接适配器需要将正常结束、取消、失败明确分开。

现有通道使用网站的签名 HttpOnly 会话 Cookie，并绑定当前 Agent 回复，**不开放匿名输入任意文本或第三方直接合成**。对方不需要、也不会获得 Boids 或 TTS API Key。请勿把网站 Cookie 作为服务间鉴权方案。

## 3. 建议交付给视频服务的协议（草案，待共同确认）

建议由我们的 Gateway 主动建立一条经过鉴权的服务端 WebSocket，转发已解码的 PCM；对方一边接收，一边生成视频。对方可提出等价的流式 SDK / HTTP 协议。

建议第一版每条连接只对应一个 `stream_id`，即一条 Agent 回复，避免并行回复混音。以下事件名及字段是拟新增约定，**目前尚未上线**。

### 开始

```json
{
  "type": "audio.start",
  "protocol_version": 1,
  "stream_id": "<opaque UUID>",
  "format": "pcm_s16le",
  "sample_rate": 24000,
  "channels": 1
}
```

对方返回 `audio.ready` 后才开始发送音频。`stream_id` 仅标识媒体流，不包含访客信息，也不是访问凭证；鉴权方式另行约定。

### 增量音频

便于初次集成的 JSON 版本示例：

```json
{
  "type": "audio.chunk",
  "stream_id": "<same UUID>",
  "seq": 0,
  "sample_offset": 0,
  "sample_count": 480,
  "data": "<960 字节 PCM 的 Base64>"
}
```

- `seq` 从 0 连续递增；`sample_offset` 表示这一分片首个采样帧相对整条音频的偏移，不是网络到达时间。
- `sample_count` 指采样帧数；当前单声道 S16LE 的解码字节数应等于 `sample_count × 2`。
- 例如 20 ms = 480 个采样帧 = 960 字节；40 ms = 960 个采样帧 = 1,920 字节。这是可选的重新分帧方案，不是当前 TTS 的分包保证。
- 视频时间轴可按 `sample_offset / 24000` 秒对齐。最后一片允许短于约定帧长，不能丢弃尾音。
- 服务端适配器需要保留未成完整采样帧的字节，跨分片拼接，不能单独丢弃奇数字节尾部。
- 若改用 WebSocket 二进制帧，需要共同定义二进制头部和序号/偏移编码；不能只凭本示例猜测格式。

### 正常结束、取消、失败

```json
{"type":"audio.end","stream_id":"<same UUID>","total_samples":96000}
```

`audio.end` 表示不会再有输入，**不表示视频已经播放完成**。视频服务仍需处理剩余音频，输出尾部视频，再发送自己的完成事件。

```json
{"type":"audio.cancel","stream_id":"<same UUID>","reason":"user_stop"}
```

取消时应立即停止当前生成、清空该流的待播音视频，返回取消确认；迟到的旧流视频帧必须丢弃。不能等积压内容播完才停止。

失败应返回带 `stream_id` 的独立 `error` 事件和可重试性说明，不携带内部密钥或敏感错误详情。第一版建议不自动断线续传或重播；恢复能力需单独定义去重和确认位置。

## 4. 音画同步与播放原则

建议链路：

```text
LLM 正文流 → 我们的 Gateway → 双向流式 TTS
                                  ↓ PCM 增量
                           视频服务流式输入
                                  ↓ 同步音视频
                              浏览器播放器
```

关键点是**不要让现有播放器立即播放音频、另一个播放器独立播放滞后的视频**，否则口型必然容易错位。

双方需选择一种播放方案：

1. 视频服务直接返回同步的音视频流（例如 WebRTC），浏览器播放该流，并停用现有独立 PCM 播放路径。
2. 视频服务只返回视频，但提供与输入音频采样时间轴对应的展示时间戳；浏览器统一缓冲和调度同一份音频与视频，不能靠网络到达时间对齐。

视频生成还会增加首帧延迟。当前 TTS 的实测响应时间不等于最终数字人延迟；双方需分别测量：LLM 首段正文、TTS 首段音频、视频首帧、浏览器首个同步音画的时间。

## 5. 对方需要提供或确认

- 是否真正支持增量输入音频、输入结束前输出视频，还是仅支持完整文件生成。
- 支持的采样率、位深、端序、声道数；最小分片、最大分片、最小驱动音频窗口。
- 输入接口、鉴权、连接建立及并发限制，以及 `ready/end/cancel/error` 的协议。
- 是否要求实时匀速输入；若可高速输入，最大待处理音频时长、背压/确认机制。不能默认无限缓冲。
- 返回视频的协议、分辨率、帧率、编码、首帧延迟，是否带同步音轨或可对齐的时间戳。
- 长时间没有新音频时的行为（保持连接、静止画面、超时）；应由双方设定超时并传播错误。
- 停止后如何清空音画队列；切换下一条回复时如何隔离上一条流。
- 数据存储/日志/保留时长及区域；音频可能包含用户对话信息，默认不做长期留存。

## 6. 我们后续负责的适配工作与验收

确认协议后，我们负责把 Gateway 中的 PCM 增量接入视频服务，补齐服务间鉴权、序号/时间轴、重新分帧或重采样、背压、取消联动及网页播放器。该工作不需要把 TTS 凭证交给对方。

当前网站保护上限包括：每会话 1 路语音、Gateway 全局 32 路订阅、每会话每分钟 12 次开启、朗读最多 8,000 字符、TTS 连接生命周期最多 120 秒、音频通道最多 330 秒。它们是当前保护配置，**不是视频服务容量或 SLA 承诺**；对接后需要按视频成本与性能重新确定。

建议共同验收：

- 未发送 `audio.end` 时就已收到首个视频帧，而非仅支持预录制文件。
- 中文、英文及混合语言回复的顺序、尾音完整，音画同步指标满足双方约定。
- 不规则分片、短句、长句、停顿、慢生成和突发快速音频输入均正常。
- 停止或切换回复后没有旧流音频/视频残留；视频异常不会导致文字对话中断。
- 验证首帧延迟、端到端延迟、并发、内存上限和网络中断时的明确错误行为。

TTS 官方协议参考：[BytePlus 双向流式 TTS](https://docs.byteplus.com/en/docs/byteplusvoice/streaming_tts)。官方支持 PCM 等流式音频输出，并支持多档采样率；本文描述的是我们现有集成配置，而非宣称所有可选能力已在网站启用。
