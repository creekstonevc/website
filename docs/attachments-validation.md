# Files migration validation

This records validation for the native Boids Files migration.

On 2026-09-18, a live upload check using the existing production server's Boids
configuration returned HTTP 404 from `POST https://api.boids.so/v1/files`.
After the provider's production rollout, a repeat check using the same production
configuration succeeded: multipart upload, metadata lookup and content download
all returned HTTP 200. The upload contract matched and downloaded bytes were
identical. The temporary QA file was deleted successfully (HTTP 200). No production
credentials were sent to staging, and no endpoint or model change was necessary.

The release preflight passed 47 Gateway tests, 20 client tests, lint, type checking,
the static production build, deployment-script syntax and Git whitespace checks.

After deployment, the public website endpoints passed a real upload → Responses
input_file → Agent marker read → generated file annotation → content download →
history restoration test. Both uploaded and generated bytes matched the test
marker. The generated-file metadata endpoint returned 404 while content worked;
a release follow-up reads its UTF-8 Content-Disposition header without buffering
the file. Uploaded test files and test conversations were deleted. Generated
file-out deletion returned 404 (provider-managed outputs were not forcibly removed).

## Automated checks

```bash
npm run gateway:test
npm run agent:test
npm run lint
npm run typecheck
npm run build
bash -n deploy.sh
```

The Gateway fixture runs a real local HTTP Gateway against deterministic Files,
Responses and Conversations mocks. It checks native multipart encoding, exact
input_file content, the supplied Boids file_path annotation structure, UTF-8
filenames, binary identity, downloaded headers, history restoration and TTS
path cleanup. It also covers:

- Final-response, output-item and incremental-annotation SSE variants.
- File-only inputs, outputs and history; genuine user Hi with an attachment.
- Incomplete streams/history and forged upstream custom events.
- Wrong-session, expired, forged, retired and wrong-direction receipts.
- User-controlled file IDs, paths, provider URLs and purpose overrides.
- Duplicate attachments, per-file/aggregate caps, unsafe names, invalid Base64.
- Unknown/wrong-ID output metadata withholding, lookup deduplication and cache reuse.
- Provider authentication/rate-limit/server errors and safe error messages.
- Bounded binary reads, content-length mismatch, Origin and signed-cookie checks.
- Transfer concurrency/rate limits and files-disabled text chat.
- Retired references displayed without any transport fallback.

## Internal-output regression (2026-10-12, local only)

The reported real sample `确认卡验收-20261010-A` showed `SKILL.md` as an
attachment. Its original conversation/response ID and raw provider events have
not been recovered from the available task evidence. No real conversations were
searched and no new production leads were created for this investigation. We
therefore cannot assert which Agent command, copy or provider export produced
that particular file.

The independently proven website defect is narrower: before this patch,
`messageAttachments` issued a valid output download ticket for a synthetic
assistant `file_path` annotation whose provider filename was `SKILL.md`.
Website code does not itself upload Agent source: its only upload path is the
explicit browser upload endpoint. Outputs arrive as upstream file annotations.

Local HTTP fixtures now cover internal files in completed/item/annotation SSE,
history restoration, private-source hints, mixed legitimate business outputs,
user-uploaded `SKILL.md`, old named/generic output tickets, unknown metadata,
and generated-file Content-Disposition with immediate body cancellation.
They exercise the actual gateway and native Files/Responses contract, with
synthetic IDs/content and no provider credentials. They prove the website guard,
not a forensic reconstruction of sample A or a guarantee against renamed/
archived internal source. Release remains coordinated with the Agent policy.

Client tests cover draft receipt validation, upload cancellation, authenticated
downloads, failure copy, completion gating, sandbox-path display and file-only
history. Existing IME, stream recovery, pagination, bootstrap and TTS tests remain.

## Local interaction fixture

```bash
node scripts/agent-qa-server.mjs
```

After building, open `http://localhost:3100/agent/`. No provider credentials or
external calls are used. Upload any small file, or send `artifact`, `file only`
or `incomplete file`. Uploaded filenames containing `slow-upload` and
`fail-upload` exercise pending/error states. Existing `long`, `retry`,
`disconnect` and `seed history` prompts cover conversation regressions.

## Release boundary

Mock tests prove website behavior against the confirmed contract; they do not
establish that a particular Boids deployment has enabled Files or that the live
Agent always emits annotations. Do not infer production rollout from the staging
screenshots. Commit, push and deployment are separate actions; retain the current
production URL/model, and verify a live upload/content round trip on release.
