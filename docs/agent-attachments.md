# Native Boids Files attachments

The website uses the existing server-side `BOIDS_API_KEY` and `BOIDS_BASE_URL`
for Files, Responses and Conversations. The production default remains
`https://api.boids.so/v1`; staging URLs and models in API examples are not
deployment configuration. Agent.md and the Agent's Skills are unchanged.

## Flow

1. The browser sends a selected file to the same-origin private Gateway.
2. The Gateway uploads multipart data to `POST /v1/files` with `purpose=user_data`.
3. Boids returns a File object. The Gateway validates it and signs a receipt bound
   to the current conversation, file ID, filename, size, direction and expiration.
4. When the founder sends their message, the browser submits receipt(s), not raw
   file IDs. The Gateway verifies ownership and constructs native Responses input.
5. On successful response completion, the Gateway reads assistant `file_path`
   annotations and issues signed download receipts. File cards retain the
   Creekstone black/gold appearance and do not expose sandbox paths as URLs.
6. A download validates the HttpOnly conversation cookie, active-session selector
   and signed receipt before fetching `GET /v1/files/{file_id}/content`.

### Upload

Browser endpoint: `POST /api/agent/attachments/upload` with same-origin cookies:

```json
{"sessionKey":"<browser-session-selector>","name":"创业计划.pdf","dataBase64":"<file-bytes>"}
```

The bounded JSON transport between browser and Gateway is retained to avoid
changing Nginx/body-limit behavior. **The upstream upload is native multipart**,
not JSON or an intermediary storage API:

```text
POST {BOIDS_BASE_URL}/files
Authorization: Bearer <server-only Boids key>
Content-Type: multipart/form-data; boundary=<generated by fetch>

purpose: user_data
file: <binary file with original UTF-8 filename>
```

Expected File fields: `id`, `object: "file"`, `filename`, `bytes`,
`purpose: "user_data"`; a `status: "error"` cannot produce an upload receipt.
An upload timeout is ambiguous: the remote file may have been stored, but it is
not automatically sent to the Agent. Retrying may create another file.

### Responses

```json
{
  "model":"<existing server-configured Agent>",
  "conversation":"<server-verified conversation>",
  "stream":true,
  "input":[{
    "role":"user",
    "content":[
      {"type":"input_text","text":"请查看这份 BP"},
      {"type":"input_file","file_id":"file-<upload-id>"}
    ]
  }]
}
```

Text-only turns and the hidden `Hi` bootstrap remain ordinary text, without
hidden attachment manifests, storage paths or extra instructions. A file-only
input uses `请查看附件。` as its visible default prompt. A genuine user `Hi`
with a native attachment is not hidden as bootstrap history.

### Generated output

The confirmed Boids contract is:

```json
{
  "type":"message",
  "role":"assistant",
  "status":"completed",
  "content":[{
    "type":"output_text",
    "text":"文件已生成：`/workspace/session/笑话.txt`",
    "annotations":[{"type":"file_path","file_id":"file-out-<id>","index":0}]
  }]
}
```

Only typed annotations from the authenticated upstream grant access. Paths,
bare IDs, Markdown links and text that resembles JSON cannot create a download.
`index` is not assumed to be a character offset. Filename/size come from
`GET /v1/files/{file_id}`; if metadata is unavailable, a safe basename from the
same message or a generic label is display-only fallback. The signed `file_id`
still determines the content fetch. Metadata lookup is time/concurrency bounded,
deduplicated and cached, so a metadata outage does not fail the text answer.

The stream supports annotations in `response.completed.response.output`,
`response.output_item.done`, and `response.output_text.annotation.added`.
Receipts are emitted only after `response.completed`, before forwarding that
terminal event. Failed, incomplete or disconnected responses cannot authorize a
download. Upstream `creekstone.*` events are discarded; only the Gateway can
emit its signed attachment and TTS metadata. A response containing only a file
is valid, even when the text is empty.

### History and downloads

Conversation history uses the same native content: user `input_file` parts and
assistant `output_text.annotations[].file_path`. Both restore to the same cards,
including file-only messages. Receipts are renewed from conversation history;
no process-local upload registry is required after restart.

Browser download: `POST /api/agent/attachments/download` with
`{sessionKey,ticket}`. The browser never receives an upstream key or a signed
provider URL. Downloads are returned as `application/octet-stream`, forced
`Content-Disposition: attachment`, UTF-8 filenames, `nosniff`, `no-store` and a
sandbox CSP. HTML/SVG files are not embedded or executed.

## Limits and security

- 5 MiB per upload/download; 3 files and 10 MiB aggregate per sent message.
- 4,000-character text validation is independent of attachment metadata.
- Two concurrent transfers globally, one per conversation. Hourly upload caps:
  10 per conversation / 120 globally; downloads: 60 / 600. Nginx also limits IPs.
- Upstream redirects are rejected, IDs have a strict character/length allowlist,
  JSON and binary reads are bounded even without a Content-Length header.
- Only server-returned valid upload IDs and native history/output annotations
  can be signed. Browser-supplied model, conversation, URL or arbitrary file ID
  cannot override these boundaries. Output receipts cannot be used as uploads.
- Receipt v2 uses a separate HMAC domain and conversation binding. Tampered,
  expired, cross-conversation and retired receipts are rejected before fetch.
- Keys are server-only, never `NEXT_PUBLIC_`. Files use the same Boids key as chat;
  the website's authorization does not replace provider-side isolation. Boids
  must ensure annotations refer to files the Agent is allowed to return.

Set `BOIDS_FILES_ENABLED=false` to disable files while keeping text chat open.
The deployment script rewrites the Gateway environment from the new template.
Retention remains an upstream concern: removing a draft does not delete a
stored file, and automatic cleanup is not part of this migration.

## Existing conversations

The previous storage transport, credentials, directory scoping, manifest
generation and path-based download authorization have been removed. There is
no fallback to that service. Retired text references/manifests are hidden for
readability only, with a re-upload/regenerate notice for actual old attachments.
Old receipts in drafts become an explicit reselect-file error. Old remote files
are not deleted or automatically copied; they have no native file IDs to use.

Protocol reference: [OpenAI file inputs](https://developers.openai.com/api/docs/guides/file-inputs),
plus the supplied Boids upload, Responses, conversation-item and download examples.
